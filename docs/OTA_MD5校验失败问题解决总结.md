## 二、问题现象

OTA 下载**总能完整结束**（字节数一字不少），但最终的全量 MD5 校验**永远失败**：

- 两次整包重下，MD5 结果**完全相同**（确定性失败，非随机位错误）；
- 每个分片写入 W25Q 后都做**回读校验且全部通过**（SPI/Flash 路径无辜）；
- 下载速度、进度上报、连接管理全部正常。

反复出现约 30 轮仍未定位，曾怀疑面包板/SPI 搬运、token、任务优先级等方向。

## 三、排查方法论（数据驱动的诊断链）

盲改无果后，建立了四层可观测/可对拍手段，最终一击定位：

| 手段 | 作用 | 关键结论 |
|---|---|---|
| RX 黑匣子（RXDIAG） | ISR 记录每次 UART 突发长度、+IPD 帧声明/提取/丢弃计数、帧首尾指纹 | esp-at 交付量=声明量，STM32 侧解复用零丢失 |
| 逐片"写→读→比对"回读校验 | 区分 SPI 错与 UART 错 | W25Q 内容 = 写入内容，SPI/面包板无罪 |
| 分块指纹（排障36 上线） | 下载完成后对每 4KB 块打「块 MD5 + 块首 8 字节」，与 PC 端同规格参考表逐块对比 | 110/110 块 first8 全对、块 MD5 全错 → 内容在块内某处系统性缺失 |
| Python 逐行复刻 md5.c | 从源码提取 64 步压缩 + 增量逻辑逐行翻译，与标准 MD5 全长度对拍 | 设备端 MD5 实现**完全正确**，排除算法嫌疑 |
| PC 暴力重建模型 | 对上传文件做「删 k 字节 @ 位置 cut」等变换，匹配设备块 MD5 | 16/16 块命中「删 1 字节」模型，缺失点收敛 |

## 四、真凶：esp-at 在 SSL 流绝对偏移 2048 处固定丢 1 字节

### 证据链

1. **分块指纹矛盾**：110 块 first8（直接读 Flash 打印）与 PC 完全一致，但块 MD5 全不一致 → Flash 内容与文件有差异，且差异不在块首。
2. **删除模型命中**：设备 B000 的 MD5 恰等于「文件在偏移 1681 处删 1 字节、后续整体前移」的内容；16/16 块全部命中，缺失点收敛到 1676~1681。
3. **2048 铁证**：缺失点(1676~1681) + 响应头长(367~372) = **2048 整**。

### 结论

**ESP32-C3 的 esp-at 固件在接收每条 SSL 数据流时，会在流的绝对偏移 2048 字节处（内部 2KB 缓冲边界）丢失 1 个字节，且是确定性行为（丢弃而非暂存）。**

### 该根因如何解释全部历史现象

| 历史现象 | 解释 |
|---|---|
| 全量 MD5 确定性失败、重下结果一致 | 丢字节是固定机制，逐字节可复现 |
| 逐片回读校验全过 | 校验的是"收到的内容"，而收到的内容本身就少了 1 字节 |
| 每块 first8 全对 | 丢失点在流内 2048 处（> 块首 8 字节），块头不受影响 |
| Range 尾垫 768B 无效 | 丢点在**流中部**而非流尾，垫底吸收不到 |
| check 响应（186B）从不损坏 | 流总长 < 2048，不触发丢失点 |
| 早前观测"每流差 1~2B" | = 流内**每个** 2048 边界各丢 1 字节（4864B 体 + 370B 头 = 5234B 流丢 2 处） |
| 早期"got=2920/2558/2549"等截断 | 同族机制的不同表现（帧边界/缓冲交互），逐一修复后暴露出本根因 |

## 五、解决方案

### 关键修复：分片大小 4096 → 1536

```
OTA_CHUNK_SIZE  4096  →  1536
```

原理：esp-at 只在流的**绝对偏移 2048** 处丢字节。设响应头长约 370B、Range 尾垫 768B：

- **1536B 片**：流总长 = 370 + 1536 + 768 = 2674B，唯一的 2048 丢点落在 **body 的 pad 区（1536~2304）**——收满 1536B 即停，写入的前 1536B 纯净；
- **末片**：剩余 284B，整条流 654B < 2048，根本没有丢点；
- 片数 110 → 293，单连接跑完，实际耗时约 1~2 分钟，可接受。

### 配套机制（全部保留，构成最终方案）

| 机制 | 作用 |
|---|---|
| Range 尾垫 768B | 让 2048 丢点与流尾吞字节都落在冗余区 |
| 上传包尾部追加 4B 0x00 | 文件尾留出可牺牲字节（make_release.py 自动完成） |
| 末片短收补零 | 末片流 <2048 无丢点，仅流尾吞 1~2B，按缺失量补 0x00 |
| 收满即停 + 队列排空 | 每片收够即停；排空队列避免下一片撞 4 槽队列保护 |
| 每片开始 FrameFlush | 清除流尾吞字节在解复用器残留的计数，防止吞掉下片帧头 |
| 头解析 + Content-Length 精确收尾 | 定位 body 起点，chunk_buf 即纯固件体 |
| 循环 DMA + ISR 先拷贝后处理 | STM32 UART 接收零丢失窗口（修复 got=2920 截断） |
| 计数制帧队列（4×2048） | ISR/任务消费对账，lost=0 |
| 逐片写后回读校验 | SPI 路径出错当场暴露 |
| 模块复位恢复 + 全链路重连 | 长会话劣化时自动恢复 |
| MD5 全量校验兜底 | 最终唯一判决，一次不过整包重下 |

## 七、经验教训

1. **确定性错误 = 系统性偏差**。同一错误 MD5 反复出现，说明不是随机位错，而是某个固定环节的固定行为——不要反复"重试"，去建观测找那个环节。
2. **分层可观测是定位的前提**：RXDIAG 黑匣子把"esp-at 交付量 vs 解复用提取量 vs 丢弃量"对账清楚；分块指纹把"内容差异位置"从 448KB 缩小到块级；最终 PC 重建模型把缺失点钉在 2048。
3. **怀疑一切，包括第三方固件**：esp-at 是闭源固件，"吞字节"这类行为只能通过协议/请求设计去规避（垫底、分片避开坏点），而不是修复它。
4. **校验必须独立于传输**：逐片回读校验证明的是"写进去的就是收到的"，全量 MD5 对照的是"文件本身"——两套校验对照才暴露出"收到的内容本身少了 1 字节"。
5. **所有代码改动经单一生成源 + 二进制字符串自检**：-O2 会把不可达的防御分支整段删除，构建后必须验证关键字符串确实在 bin 里（曾因此漏发一版）。
