# STM32 + ESP-AT 远程 OTA 开发：流程与故障排查手册

> 适用：STM32F407 + ESP32-C3(AT固件) + OneNET 融合版 OTA + W25Q128 三区（当前/下载/备份）
> 本文回答三个问题：①遇到了什么问题、怎么解决的 ②再次遇到怎么快速解决 ③怎么让 OTA 开发更流畅
> 排障全过程见《OTA远程升级开发文档_BootLoader_W25Q64_OneNET.md》（排障1~37）

---

## 一、遇到的问题与解法（按层归类）

### A. 平台/协议层（OneNET）

| 问题 | 根因 | 解法 |
|---|---|---|
| check 返回 `10403 invalid authorization` | token 的 res 资源类型与 key 不匹配：本账号融合版 OTA 只认 `res=products/{产品ID}` + **产品级 AccessKey**；`userid/` + 账号级 key 全部被拒 | token 格式 `version=2022-05-01&res=products%2F{pid}&et={ts}&method=sha1&sign=...`；用产品 AccessKey（base64）做 HMAC-SHA1，输出 URL 编码 |
| check 返回 `12012 not exist` | 上一轮任务被设备作废/取消后，旧任务号失效 | 控制台取消旧任务重新发起 |
| 下载中途服务器关链 | HTTP `Connection: close` 触发 esp-at 丢弃未打印的尾部数据 | 请求一律**不带** close（HTTP/1.1 默认 keep-alive），读满后自己 AT+CIPCLOSE |
| 服务器响应内容与文件不符 | —— | 极少见，PC 复刻同一 Range 请求逐字节对比即可排除 |

### B. 传输模块层（esp-at 固件行为，最重要）

| 问题 | 根因（实测） | 解法 |
|---|---|---|
| **全量 MD5 确定性失败（本工程最大坑）** | **esp-at 在每条 SSL 流的绝对偏移 2048 处固定丢 1 字节**（内部 2KB 缓冲边界，丢弃非暂存）；丢点在流中部，Range 尾垫吸收不到 | 分片 ≤ 2048-头长(~370) → 用 1536B 片，使 2048 丢点落在响应体冗余区 |
| 每条流尾被吞 1~2 字节 | esp-at 流尾字节丢失（= 流内每个 2048 边界各丢 1） | 请求 Range 尾部多要 768B；上传包末尾垫 4B 0x00；末片短收按缺失补零 |
| check/下载流混入旧数据（`{"results":[...` 心知天气 JSON） | esp-at SSL 缓冲关链后不清零，下一条连接的响应流被旧缓冲尾流污染；跨模块复位仍可能复现（固件行为） | ①OTA 前复位模块（PreFlight，全新缓冲）②解析器对数据流做帧级剔杂（整令牌 memcmp+括号深度，勿用逐字节过滤）③下载通道不走剔杂（固件体含同名字串会自噬） |
| 长会话（40+ 片）后流截断/劣化 | esp-at 长 keep-alive 会话内部状态劣化，重连救不了 | 分片重试 5 次，第 4 次升级为**模块复位恢复**（AT+RESTORE→重连 WiFi→重建 SSL） |
| 回显文本混入接收流 | 历史命令回显被复现污染 | 初始化后 `ATE0` 关回显 |
| `+IPD,<len>:` 帧头被当数据 / 帧头被吞 | 旧实现按字节计数切分，未按 esp-at 协议长度剥离 | 驱动层**解复用器**：按 `+IPD,len:data` 协议字段剥离纯数据入队，控制文本与数据物理隔离 |
| CIPSEND 握手错乱 | `OK`/`>`/`SEND OK` 任意合并分帧 | 粘性标志：ISR 检测到 `>`/`SEND OK` 置位，任务轮询而非逐帧配令牌 |

### C. 主机侧（STM32）固件层（自己的坑）

| 问题 | 根因 | 解法 |
|---|---|---|
| 固定 got=2920/2048+872 截断 | **RX DMA 每次 IDLE 复位**的两处竞态：复位窗口内到达字节丢失；重使能后 DMA 从头覆盖缓冲而 ISR 仍在读 | 循环 DMA 永不停机 + ISR 先线性化拷贝后处理（环缓冲） |
| 大突发丢帧（lost>0） | 帧队列 head/tail 指针模型歧义；ISR 处理大突发期间消费者停摆导致整帧丢弃 | 计数制槽队列：`g_dm_closed`/`dm_popped` 双计数 + 4×2048 分槽，队满时槽保持开启 |
| 解析字段错乱（md5 脏、缺字段） | 重写时把拷贝循环写成 `out[i++] = *p++`（for 自带 i++，跳字） | 防御：md5 只留十六进制并断言 32 位；重构后对照原函数逐行 diff |
| 剔杂跳过器自伤（`{"code`→`{ode`） | 逐字节部分匹配把真实字节吃掉且无法撤回 | 帧级两遍处理：整令牌 memcmp、括号深度剔除、帧尾 carry 跨帧拼接 |
| 收满即停后下一片失败（got=2549 恒定） | 提前退出留下未消费垫尾帧，下一片撞 4 槽队列保护 → 关闭被拒 → 无信号量 | break 条件 = `收满 && 队列排空`；每片开始 FrameFlush |
| 模块复位恢复后 CIPSEND ERROR | 恢复后未重建 SSL 连接 | 恢复路径无条件重连 |
| 防御分支凭空消失 | **Keil -O2 死代码消除**：重试块以 continue 结尾使后续分支被判不可达整段删除 | 分支放到可达位置；构建后**在 bin 里搜关键字符串自检** |
| AT 探活全败但模块在线（热点可见设备） | RX 改循环 DMA 时漏改 `DMA_Memory0BaseAddr`（仍指旧缓冲） | 结构改造后逐行核对 DMA 配置项 |

## 二、再次遇到怎么快速定位（决策树）

> 通用第一步：看日志里的**固件身份证行** `[OTA] FW 1.1.0 (built ...)`，确认烧的是最新固件——排障史上多次"改了没烧"。

### 症状 1：分片收不满 / 下载中断（got < want）
```
RXDIAG 里 lost > 0          → 帧队列/解复用问题（槽队列消费停摆、残留计数吞帧头）
RXDIAG 里 lost == 0 但 got 恒定截断 → 看 decl 帧声明 vs 期望：esp-at 交付结构问题
got 每次相同（确定性）       → 时序/缓冲机制问题，不是随机干扰
```
修复方向：队列排空不变量、每片 FrameFlush、分片大小、模块复位恢复。

### 症状 2：下载完整但 MD5 不匹配（本工程核心症状）
```
第一步：分块指纹（每 4KB 块打 md5+first8），与 PC 同规格表对比
  - 个别块错 → 该片接收/写入问题，查对应片的日志与 decl
  - 110/110 块 first8 全对、md5 全错 → 流中部系统性丢字节（esp-at 2048 机制）
     验证：PC 对文件做「删 k 字节 @ cut」扫描，命中设备块 md5 即确认
     修复：分片调到 2048-头长 以下（本项目 1536），使丢点落 pad 区
  - first8 都错 → 头解析/对齐问题（body 起点错位）
```
配套自检：用 Python 逐行复刻设备端 MD5/解析逻辑与标准对拍，先排除自家算法。

### 症状 3：响应流混入陌生数据 / 字段错乱
```
混入旧 JSON（{"results":...） → esp-at 缓冲滞留：OTA 前复位模块 + 帧级剔杂
字段错位跳字                  → 自家解析 bug：逐行复刻对拍定位
```

### 症状 4：连接/握手失败
```
CIPSTART 失败 → 看 resp；恢复类路径记得重建连接
MQTT 在线但 CIP 异常 → 互不干扰（独立链路），看 esp-at 状态
```

### 症状 5：行为完全随机、无法复现
```
优先怀疑：烧错固件（身份证行）、内存覆盖（大缓冲 static 化）、任务栈溢出
```

## 三、esp-at 传输层避坑清单（铁律，开发前先读）

1. **单条 SSL 流 ≥ 2KB 会在 2048 字节边界丢 1 字节**——分片或请求设计必须让"绝对偏移 2048"落在不在乎的字节上；
2. **每条流尾被吞 1~2 字节**——所有响应消费都要留冗余/垫底；
3. **关链后 SSL 缓冲不清零**——事务间留隔离，关键操作前复位模块；
4. **别用 `Connection: close`**——服务器关链时 esp-at 丢未打印尾部；
5. **必须 `ATE0`**——回显会污染数据流；
6. **数据按 esp-at 声明长度剥离（解复用），主机侧绝不按字节数硬切**；
7. **长会话会劣化**——重试链要含"复位模块"级恢复；
8. 小响应（<2KB）是安全的——可用来做探针/对照。

## 四、怎么让 OTA 开发更流畅（流程建议）

### 1. 可观测性当作功能做，不是临时手段
- 每个环节有"量"：突发长度、帧声明/提取/丢失计数、每片 got/want、块指纹；
- 固件身份证打印（版本+编译时间），杜绝"改了没烧"；
- 失败路径自动带出诊断（响应头 + RXDIAG），一条日志能定位。

### 2. 单一生成源 + 构建后自检
- 手改多轮 = 状态失控（本项目教训）。用 `源文件 + 增量脚本(gen_final.py) → 生成实装稿`，所有修改收敛在脚本里，可重放可追溯；
- 每次构建后**在 bin 里搜关键字符串**：验证新代码真在固件里（-O2 会删不可达代码、烧错文件等问题一次暴露）；
- 一键发布脚本（make_release.py）：自动换版本号→编双版本→垫尾→导出。

### 3. PC 对拍与模拟（不烧板先验证）
- PC 复刻请求：验证服务器行为（Range、CL、关链时机）；
- PC 同规格参考表：指纹、md5 对照；
- Python 逐行复刻设备算法：解析、MD5、校验逻辑先与标准对拍。

### 4. 一次只改一个变量 + 保持可回退基线
- 分片大小、pad 长度、片数这类参数单变量实验；
- 每版固件有唯一 md5 记录，失败时能对照"哪个改动引入"；
- patch 失败立即回滚重生成，不做增量修补考古。

### 5. 受控实验隔离变量
- 用编译开关（如 WEATHER_DIAG_SKIP）把怀疑的子系统整体摘除，纯净环境验证。

### 6. 分层防御：每层有自己的校验
- 传输层：解复用对账（lost=0）；
- 存储层：写→读→比对回读校验（错则擦重写一次）；
- 文件层：全量 MD5 对照平台（最终判决）；
- 应用层：Boot 搬运后新固件启动确认（COMMITTED→备份 Zone2，失败回滚）。

### 7. 排障记录制度化
- 每次问题一行式记录：现象/根因/修复/验证状态，编号连续（排障N）；
- 积累成上面的避坑清单，下个项目直接受益。

### 8. 版本与包管理纪律
- 版本号三处一致：`ota_config.h` 的 FW_VERSION / OneNET 升级包 / 设备上报；
- 上传包文件名纯 ASCII（OneNET 不认中文）；
- token 生成脚本化，过期即换，构建时自检双重编码。

## 五、完整开发流程全景（从零到一）

```
① 平台与架构
   选平台（OneNET 融合版 OTA）→ 三区规划（当前 APP 区 / Zone1 下载区 / Zone2 备份区）
   → 状态标志区（升级标志/保护标志/版本/MD5）→ BootLoader 搬运与回滚逻辑
   （Boot 先行自测：JEDEC 读、擦写回读、标志 R-M-E-W 全过再跳 APP）

② 最小链路打通（先用小文件/旧固件）
   check（鉴权 token 先过）→ 下载 1 片 → 写 W25Q → 全量 MD5 → READY → Boot 搬运 → 版本上屏
   此阶段只验证"路通"，不追求大文件

③ 上观测
   RX 黑匣子、事务日志、固件身份证、失败诊断打印

④ 迭代加固（传输层逐坑填平，对照第三节清单）
   解复用 → 循环 DMA → 帧队列对账 → 剔杂/事务隔离 → 分片与垫底策略 → 恢复链
   每个修复 = 一次受控复测（改一个变量，看一个指标）

⑤ 全链路验证 + 回归清单
   □ check 响应干净     □ 每片 got 满足    □ lost=0
   □ 块指纹 = PC 表     □ MD5 OK          □ READY→Boot 搬运成功
   □ 新固件上屏运行     □ Zone2 备份完成   □ 回滚路径可用

⑥ 发布
   make_release.py 出双版本（上传包/设备端）→ OneNET 传新包 → 烧设备端 → OTA 页验证
```

## 六、一句话总结

**OTA 开发 90% 的难度在传输层而不是业务逻辑**：esp-at 这类闭源 AT 固件有确定性的丢字节/缓冲污染行为，不可修复只能规避——所以开发的正确姿势是：小步验证、全程可观测、PC 对拍先行、把每个"确定性怪象"用数据钉死再动手，而不是反复重试或猜。
